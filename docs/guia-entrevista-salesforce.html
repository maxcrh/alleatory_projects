1. Apex e Desenvolvimento Core

1.1 Bulkification e limites de governador

PerguntaEm um ambiente bancário com alto volume, como você garante que seus triggers e classes Apex não estourem os governor limits? Dê exemplos concretos.
Resposta esperada
  • Nunca fazer SOQL/DML dentro de loops; coletar IDs em Set/Map e consultar/atualizar em lote.
  • Uso de Map<Id, SObject> para evitar queries repetidas.
  • Limites: 100 SOQL síncronos, 150 DML, 50k registros por query, 10s/60s CPU time.
  • Processamento assíncrono (Queueable, Batch Apex, @future) para operações pesadas.
  • Padrão de trigger handler único por objeto com lógica delegada a classes de serviço.
Cenário realUm trigger de Account começou a falhar em importações de 5.000 registros com erro de "Too many SOQL queries". O código fazia uma query dentro de um for. Como você investiga e corrige? Boa resposta: mover a query para fora do loop, usar Map indexado por chave, e validar com um teste que insere 200+ registros.
🚩 Alerta: candidato que só fala "boas práticas" sem citar números de limites ou que nunca usou Batch/Queueable.

1.2 Arquitetura de Triggers

PerguntaQual padrão de arquitetura de trigger você usa e por quê?
Resposta esperada
  • One trigger per object + Trigger Handler (framework próprio ou Trigger Actions Framework / fflib).
  • Separação de responsabilidades: trigger só delega, lógica fica em handler/service.
  • Controle de recursão (static flags) para evitar reentrância.
  • Desligar automações via Custom Metadata / Custom Settings sem deploy.
Cenário realDois times mexem no mesmo objeto Case. Como você evita que um trigger de um squad quebre o do outro e garante ordem de execução previsível?
🚩 Alerta: múltiplos triggers no mesmo objeto sem controle de ordem.

1.3 Testes e cobertura

PerguntaAlém dos 75% obrigatórios, o que torna um teste Apex realmente bom?
Resposta esperada
  • Testes que validam comportamento e asserts reais, não só cobertura.
  • Uso de @testSetup, Test.startTest()/stopTest() (para limites e async).
  • Cenários positivos, negativos e bulk (200 registros).
  • HttpCalloutMock, Test.setMock para callouts; Test Data Factory; sem SeeAllData=true.
Cenário realUm PR tem 90% de cobertura mas nenhum System.assert. Você aprova? Como lida com o desenvolvedor? Boa resposta: não aprova; explica que cobertura ≠ validação, e pede asserts significativos.

2. Integrações (REST / SOAP)

2.1 Callouts e resiliência

PerguntaComo você estrutura uma integração REST síncrona para um sistema bancário legado, considerando confiabilidade e timeout?
Resposta esperada
  • Named Credentials para autenticação (sem hardcode de credenciais).
  • Tratamento de timeout (120s cumulativo, 10 callouts por transação).
  • Retry/idempotência; para operações críticas, filas assíncronas (Platform Events, Queueable).
  • Logging estruturado com correlação (trace id).
  • Nunca callout dentro de trigger síncrono (usar @future(callout=true) ou Queueable).
Cenário realA API do core bancário cai intermitentemente e algumas transações duplicam. Como você garante idempotência e evita registro duplicado? Boa resposta: chave de idempotência enviada ao backend, verificação de resposta, dead-letter queue, reprocessamento controlado.
🚩 Alerta: credenciais em código, callout síncrono em trigger, sem tratamento de retry.

2.2 REST vs SOAP e segurança

PerguntaQuando faz sentido usar SOAP em vez de REST, e como você protege os dados em trânsito em ambiente regulado?
Resposta esperada
  • SOAP: contratos WSDL rígidos, sistemas legados, transações formais.
  • REST: mais leve, JSON, integrações modernas.
  • Segurança: TLS, mTLS quando exigido, Named Credentials, OAuth 2.0, Shield Platform Encryption.
  • Conformidade com LGPD e políticas do banco (mascaramento, auditoria).

3. Lightning Web Components (LWC)

3.1 Comunicação e performance

PerguntaComo componentes LWC se comunicam entre si e com Apex, e como você otimiza performance?
Resposta esperada
  • Pai→filho via @api; filho→pai via CustomEvent.
  • Irmãos via Lightning Message Service (LMS) ou pub/sub.
  • Apex via @wire (reativo, cacheável) vs. chamada imperativa.
  • @AuraEnabled(cacheable=true) para leituras; evitar re-renders.
  • Lazy loading, paginação server-side para grandes volumes.
Cenário realUma tela com uma lista de 10.000 Cases trava o navegador. Como você resolve? Boa resposta: paginação/lazy load no servidor, lightning-datatable com infinite scroll, não carregar tudo de uma vez.
🚩 Alerta: candidato que não distingue @wire de chamada imperativa, ou que carrega tudo no client.

3.2 Segurança no LWC

PerguntaComo você garante que o LWC respeite as permissões do usuário (FLS/CRUD)?
Resposta esperada
  • Segurança no Apex (WITH SECURITY_ENFORCED, Security.stripInaccessible, isAccessible()).
  • Não confiar apenas na UI; enforcement no servidor.
  • Contexto bancário: princípio do menor privilégio, perfis e permission sets.

4. Service Cloud / CRM

PerguntaQuais automações nativas vs. código você usa para operações de Service Cloud, e como decide entre Flow e Apex?
Resposta esperada
  • Nativo primeiro: Omni-Channel, Case assignment/escalation rules, Entitlements/Milestones, Macros.
  • Flow para automação declarativa; Apex quando há lógica complexa, bulk pesado ou integração.
  • Clicks-not-code quando possível (manutenção, governança).
Cenário realO negócio quer rotear casos por SLA, prioridade e skill do agente. Você faz com Omni-Channel + Flow ou Apex? Justifique.

5. DevOps Center e Release Management

Diferencial forte do perfil. Aprofunde bastante aqui se a vaga envolve release/governança.

5.1 Pipeline e governança

PerguntaDescreva seu fluxo de release no DevOps Center. Como você garante rastreabilidade e controle de mudanças entre ambientes?
Resposta esperada
  • Work items vinculados a user stories, controle do que entra em cada ambiente.
  • Pipeline source → integration → UAT → produção, com gates de aprovação.
  • Rastreabilidade: cada mudança ligada a um work item e a um release.
  • Backup/rollback plan, janela de deploy, validação pós-deploy.
  • Diferença entre DevOps Center e Gearset/Copado (limitações).
Cenário realUm deploy para produção falhou no meio por falha de teste de uma classe que não era do seu squad. Como você diagnostica, comunica e recupera o ambiente? Boa resposta: validação com Run Specified/Local Tests antes; análise do log de deploy; comunicação com o squad dono da classe; rollback ou hotfix controlado; retrospectiva de processo.
🚩 Alerta: candidato que "faz deploy direto" sem gates, ou não sabe explicar rastreabilidade.

5.2 Conflitos de merge e dependências

PerguntaComo você lida com conflitos entre múltiplos squads (97 devs) alterando os mesmos metadados?
Resposta esperada
  • Estratégia de branching, divisão de ownership por domínio/objeto.
  • Comunicação entre líderes, calendário de releases.
  • Custom Metadata para reduzir conflitos de deploy.
  • Resolução de conflitos no DevOps Center, revisão de componentes compartilhados.

6. Marketing Cloud (Unidas)

6.1 Journey Builder e omnichannel

PerguntaExplique como você estrutura uma jornada omnichannel (e-mail + WhatsApp) no Journey Builder com segmentação.
Resposta esperada
  • Entry source (Data Extension, API event, Salesforce Data).
  • Decision splits, wait, engagement splits.
  • Integração WhatsApp via provedor/parceiro MC ou API.
  • Automation Studio para preparação de dados (SQL em Data Extensions, imports).
  • Deliverability, opt-out, LGPD.
Cenário realUma campanha de WhatsApp precisa disparar só para clientes que não abriram o e-mail em 48h e que ainda têm contrato ativo. Como você monta isso? Boa resposta: engagement split por abertura, wait de 48h, decision split com dado de contrato (via Data Extension sincronizada do Core), filtro de opt-in.

6.2 Integração MC ↔ Salesforce Core

PerguntaComo os dados fluem entre o Salesforce Core e o Marketing Cloud? Quais os cuidados?
Resposta esperada
  • Marketing Cloud Connect, Synchronized Data Extensions.
  • SQL em Automation Studio para transformar/segmentar.
  • Cuidados: latência de sync, consentimento/LGPD, qualidade de dado, deduplicação.
🚩 Alerta: candidato que trata MC e Core como se fossem o mesmo produto (são plataformas distintas).

7. Liderança Técnica e Governança

Perfil atua como 1 dos 4 líderes de uma frente de 97 devs. Avalie liderança técnica, não só código.

  1. "Como você resolve um impedimento técnico que está travando vários squads ao mesmo tempo?"
    Espera-se: priorização, escalonamento, solução paliativa + definitiva, comunicação transparente.
  2. "Um desenvolvedor sênior discorda da sua decisão de arquitetura. Como você conduz?"
    Espera-se: abertura técnica, decisão por trade-offs, não por hierarquia.
  3. "Como você garante padronização de código e qualidade com 97 devs?"
    Espera-se: code review, guidelines, static analysis (PMD/CodeScan), templates, pairing, definition of done.
  4. "Como você apoia o PO na estruturação de histórias? Dê um exemplo de uma história mal escrita que você refinou."
    Espera-se: critérios de aceite claros, quebra técnica, viabilidade, estimativa.
  5. "Descreva uma situação em que equilibrou prazo vs. dívida técnica em ambiente bancário regulado."
🚩 Alerta geral de liderança: respostas genéricas sem exemplos concretos, foco só em código e nenhum em pessoas/processo.
